# ระบบ 05 — สมัครสอบบาลี/บาลีศึกษาและค้นผลสอบ

สถานะเอกสาร: ขอบเขตและ UI ต้นแบบ TEST_ เท่านั้น · ปรับปรุง 15 ตุลาคม 2026

## ขอบเขต

- บัญชีสมัครบาลีสนามหลวงและบาลีศึกษาสำหรับบรรพชิต/คฤหัสถ์ โดยแยก `applicant_kind` ออกจาก `pali_track`; อ้างอิง `Person`, `Organization` และ `ExamSession` ชุดเดียวกับระบบอื่น
- แยกส่วนกลางและส่วนภูมิภาค; ในต้นแบบส่วนกลางใช้ label `TEST_ส่วนกลาง · ศ.2`, ส่วนภูมิภาคใช้ `TEST_ส่วนภูมิภาค · ศ.2 / ศ.3`
- แยก ศ.2 ซึ่งเป็นบัญชีสมัคร กับ ศ.3 ซึ่งแหล่งที่ตรวจพบอธิบายเป็นบัญชีเรียกชื่อ/เอกสารดำเนินการสอบสำหรับส่วนภูมิภาคในกรณีที่เกี่ยวข้อง ไม่ใช้ ศ.3 แทนใบสมัครโดยอัตโนมัติ
- แบบเพิ่มร่างรับค่า `TEST_` เท่านั้นและเก็บใน browser memory; ยังไม่ตรวจคุณสมบัติหรือส่งบัญชีไปหน่วยงาน
- หน้าค้นผลสอบมีตัวกรองปีการศึกษา ชั้น/ประโยค ชื่อ/ฉายา/นามสกุล วัด สำนักเรียน/จังหวัด และเลขลำดับ/เลขประกาศ แต่ยังไม่มี result release หรือแถวผลสอบให้ค้น

## Use case และเกณฑ์รับมอบ

| Use case | Actor / trigger | เกณฑ์รับมอบต้นแบบ |
| --- | --- | --- |
| สมัครสอบบาลี/บาลีศึกษา | เจ้าหน้าที่สำนักเรียนกดสร้างร่าง | ระบุประเภทบรรพชิต/คฤหัสถ์, ชั้น/ประโยค, ส่วนกลาง/ภูมิภาค, สำนักเรียนและ ExamSession; ทุกค่า TEST_; บันทึกเฉพาะใน memory |
| ตรวจบัญชีสมัคร | เจ้าหน้าที่เปิดทะเบียน/กรองส่วนงาน | แสดงรหัสบุคคล/รายการแบบบัญชีและรอบสอบจาก fixture TEST_; เปลี่ยน filter ได้; ช่องติดต่อส่วนบุคคลไม่แสดง |
| ค้นผลสอบรายปี | ผู้เรียนหรือผู้ใช้ที่ได้รับสิทธิ์เลือกค้นหา | ค้นตามปีการศึกษา, ประเภทบาลี/บาลีศึกษา, ชั้น/ประโยคและฟิลด์อ้างอิงได้เฉพาะ TEST_; ถ้าไม่มี approved release ต้องแสดงว่ายังไม่มีข้อมูล ห้ามสรุปว่าสอบตก |
| เปิดรายละเอียด/ส่งออก | เจ้าหน้าที่กดดูหรือ export | แสดง/export เฉพาะข้อมูลจำลองและ metadata ของแบบบัญชี; production ต้อง authorize read/export แยก role+scope ฝั่ง server/DB |

## กฎข้อมูลและความปลอดภัย

- `Person` ไม่ใช่ user account; ผู้สมัครไม่จำเป็นต้องมีบัญชีเข้าใช้ระบบ
- `ExamSession` อ้างอิงรอบสอบ ไม่ใช้ปีปฏิทินแทนปีการศึกษา; ปีการศึกษาเก็บเป็นรหัส/ค่าแยกที่เจ้าของงานรับรอง
- ศ.2/ศ.3 เป็น form metadata/provenance ของบัญชี ไม่ใช่สถานะผลสอบ
- ผลสอบเป็นข้อมูลอ่านอย่างเดียวจาก immutable approved release; ต้องแยกบาลีสนามหลวง/บาลีศึกษา ชั้นและรอบ/ครั้งสอบ พร้อม field allowlist, revision, provenance และวันถอน release
- ไม่พบชื่อในชุดที่เผยแพร่ไม่แปลว่าสอบตก; แสดง “ไม่พบในชุดข้อมูลที่ค้น” หรือ “ไม่มีชุดเผยแพร่” ตามความหมายที่ตรวจสอบได้เท่านั้น
- ต้นแบบไม่ใส่ชื่อจริง เลขประจำตัว อายุ วันเกิด ผลสอบ คะแนน เลขสอบจริง คำอนุมัติหรือลายเซ็น

## Data design ที่เสนอ — ยังไม่ใช่ migration production

`pali_application` ผูก `person_id`, `organization_id`, `exam_session_id`, `applicant_kind`, `pali_track`, `pali_level`, `application_form_code`, `application_revision_id`, `status_code`, `submitted_at`, `effective_at`, `recorded_at`, `provenance` และ `idempotency_key`.

`pali_result_release` ระบุปีการศึกษา, track, level, session/attempt, immutable revision, provenance, allowlist, approver ตาม policy ที่ยืนยัน, published/withdrawn timestamps. `pali_result_entry` เก็บผลจากเอกสารต้นทางที่ตรวจรับแล้วและผูกบุคคลอย่างไม่กำกวม; การนำเข้าใช้ staging/preview, maker-checker, transaction, unique keys, optimistic lock และ audit. ไม่สร้าง record เมื่อไม่มีหลักฐานผลสอบ.

- ผู้รับผิดชอบและ field mapping ของผู้สมัคร ศ.2, บัญชี ศ.3, ประเภทบาลีศึกษา, การแก้รายการ และเส้นทางส่งบัญชีส่วนกลาง/ภาค/จังหวัด
- ปีการศึกษา, รอบ/ครั้งสอบ, ชั้นที่เปิดสอบ, เกณฑ์ตรวจชื่อซ้ำ/เลขบัตร และกรณีสมัครหลายสนาม
- ผู้เผยแพร่ผลสอบ, field allowlist, retention, การแก้ประกาศ/ถอน release, cache invalidation และสิทธิ์ค้นผลสาธารณะ
- policy role/scope, maker-checker, audit, สิทธิ์ export และระยะเวลาเก็บข้อมูลส่วนบุคคล

เจ้าของที่ต้องยืนยัน: เจ้าของทะเบียนบาลีสนามหลวง/บาลีศึกษา, สำนักเรียนส่วนกลาง, สำนักเรียนคณะจังหวัด/เจ้าคณะภาค และผู้รับผิดชอบข้อมูลผลสอบ (ระบุผู้แทนจริง `TO VERIFY`).

## ข้อจำกัดของ prototype

ไม่มี backend, authentication, RLS, audit, storage หรือ result release. คำค้นที่ยอมรับในโหมดนี้ต้องขึ้นต้น `TEST_`; ไม่มีการนำชื่อหรือผลสอบจริงจากเว็บไซต์ตัวอย่างมาใส่ใน fixture.
