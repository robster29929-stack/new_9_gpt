# ระบบ 01 · ทะเบียนบุคคลและตำแหน่ง

สถานะ: UI prototype สำหรับข้อมูล `TEST_` เท่านั้น · ไม่มีฐานข้อมูลจริงและไม่มีบัญชีผู้ใช้

ค่าในตัวอย่างขึ้นต้น `TEST_`; ข้อมูลจริง รายการตำแหน่ง และโครงสร้างการแต่งตั้งยังต้องให้เจ้าของทะเบียนยืนยัน

## การตรวจตำแหน่งฝ่ายการศึกษาซ้ำ/ทับซ้อน

- ช่องตำแหน่งฝ่ายการศึกษาเป็น checkbox หลายค่า และข้อมูลที่จัดเก็บ/ส่งออกใช้ ` | ` คั่นรายการ
- เมื่อเลือกหลายตำแหน่ง ระบบแสดงคำเตือนให้ตรวจสอบตำแหน่งที่อาจซ้ำหรือทับซ้อน แต่ไม่ปฏิเสธการบันทึกร่าง เพราะนโยบายวินิจฉัยยังไม่ได้รับการยืนยัน
- เมื่อชื่อบุคคลตรงกับระเบียนที่มีตำแหน่งฝ่ายการศึกษาอยู่ ระบบแสดงคำเตือนให้ตรวจว่าเป็นคนเดียวกันหรือไม่ ชื่อที่ตรงกันเป็นเพียงสัญญาณตรวจทาน ไม่ใช่การรวม/แก้ข้อมูลอัตโนมัติ
- รายการนำเข้า Excel/CSV แสดงคำเตือนต่อแถวและยังให้ผู้ตรวจทานตัดสินใจ; ข้อมูลผิดรูปแบบหรือรหัสซ้ำในไฟล์ยังเป็นข้อผิดพลาดที่ป้องกัน commit
- แบบฟอร์มและ validator ต้องมีตำแหน่งทางการปกครองอย่างน้อยหนึ่งรายการ หรือเลือกตำแหน่งฝ่ายการศึกษาอย่างน้อยหนึ่งรายการ

## การแสดงผลและการทดสอบ

- ตารางแยกคอลัมน์ตำแหน่งทางการปกครองกับตำแหน่ง จศป. ฝ่ายการศึกษา และแสดง badge เมื่อตัวอย่างมีหลายตำแหน่งฝ่ายการศึกษา
- รายละเอียดแยกกลุ่มตำแหน่งทั้งสอง และแสดงคำเตือนที่ตรวจพบ
- ช่อง “ภาค (เลือกภาค 1–18)” อยู่ถัดจากจังหวัดในแบบฟอร์ม มี 18 ตัวเลือก และค่าที่ใช้ใน fixture เริ่ม `TEST_ภาค_`
- คำค้นหาไม่ฝังเบอร์โทร อีเมล หรือ LINE ID ใน HTML แถว
- Excel template/export และ CSV มีคอลัมน์ตำแหน่งสองช่อง; ตำแหน่งฝ่ายการศึกษาหลายรายการคั่นด้วย ` | ` เพื่อให้ round-trip ได้
- CSV ไม่ส่งออกข้อมูลติดต่อหรือข้อมูลเหตุสถานะของบุคคล; XLSX template/export ของทะเบียนบุคคลก็ไม่รวมช่องทางติดต่อ
- รายละเอียดแสดงช่องทางติดต่อในส่วนที่ระบุว่า “จำกัดสิทธิ์” เพื่อทดสอบ layout โดยค่าทั้งหมดเป็น `TEST_`
- แบบเพิ่มระเบียนมีช่องติดต่อไม่บังคับ; ค่าที่กรอกทุกค่าต้องขึ้นต้น `TEST_`; สร้างร่างใน memory ของหน้าเว็บเท่านั้น
- ตัวกรองทะเบียนเลือกประเภทเหตุสถานะได้ครบ 4 ประเภท; fixtures แสดงเพียงตัวอย่าง `TEST_` และไม่ได้หมายถึงคำสั่งหรือผลพิจารณา
- รายละเอียดแยกประเภทเหตุสถานะ, ข้อความสถานะ, วันบันทึก, วันมีผล และหลักฐาน; วันที่จริงและหลักฐานใน fixture เป็น `TO VERIFY`/ไม่มีข้อมูลจริง

## TO VERIFY ก่อนนำข้อมูลจริงเข้า

เจ้าของทะเบียนข้อมูลบุคคลและผู้รับผิดชอบคุ้มครองข้อมูลต้องยืนยันแหล่งอ้างอิงและรูปแบบชื่อ/ตำแหน่ง, นิยามแท่ง/แผนก, โครงสร้างหนและความสัมพันธ์กับองค์กร, เขตข้อมูลที่จำเป็นในแต่ละประเภทบุคคล, ผู้มีสิทธิ์อ่าน/แก้ไข/ส่งออกตาม role+scope และวันมีผล, วัตถุประสงค์/ฐานการใช้ข้อมูลติดต่อ, ผู้รับผิดชอบแก้ไข, ระยะเก็บรักษา, ขั้นตอนและผู้มีอำนาจพิจารณาสถานะทั้ง 4 ประเภท, นิยามวันรับเรื่อง/วันบันทึก/วันมีผล, หลักฐานประกอบ, audit และนโยบายเผยแพร่สาธารณะ รวมถึงหลักเกณฑ์ว่า role ใดห้ามควบหรือถือซ้ำกัน

เมื่องาน backend เริ่ม ต้องไม่ส่งช่องทางติดต่อให้ client ที่ไม่มีสิทธิ์อ่าน และต้องตรวจสิทธิ์ซ้ำที่ server/API และฐานข้อมูลก่อน read/edit/export/download รวมถึงบันทึก audit ตาม policy ที่องค์กรยืนยันแล้ว
